# Data models elsewhere: research

> Status (2026-10-06), branch `data-model`: the third of four documents. What comparable systems actually do (schemas, identifiers, retention, invalidation), from their primary sources, and what transfers to cmd's single-user SQLite core. Gathered for the plan in [28](28-data-plan.md), against the requirements in [26](26-data-requirements.md). ## 1. Event sourcing and event logs in local, single-user apps

Sources: Kleppmann, *Turning the database inside-out* (2015, martin.kleppmann.com/2015/03/04/turning-the-database-inside-out.html); Fowler, *Event Sourcing* (martinfowler.com/eaaDev/EventSourcing.html); Dudycz, *Simple patterns for event schema versioning* (2021, event-driven.io/en/how_to_do_event_versioning/); *An empirical characterization of event sourced systems and their schema evolution* (2021, arxiv.org/abs/2104.01146); LiveStore concepts and state schema (2025–26, docs.livestore.dev/reference/concepts/, …/state/sqlite-schema/); *Reverse-engineering Linear's sync engine* (2024, github.com/wzhudev/reverse-linear-sync-engine); cr-sqlite `crsql_changes` (vlcn.io/docs/cr-sqlite/api-methods/crsql_changes); Kafka log compaction (docs.confluent.io/kafka/design/log_compaction.html); Figma LiveGraph (2021, figma.com/blog/livegraph-real-time-data-fetching-at-figma/); Notion's block model (2021, notion.com/blog/data-model-behind-notion).

- Kleppmann's four cases (replication, secondary indexes, caches, materialised views) all reduce to "append-only log plus derived views rebuilt by replay"; cache invalidation disappears because views are recomputed in log order, and new views are added without touching the write side.
- Fowler: snapshots are an optimisation (restore the last one, replay the tail). The hard part is external effects during replay: suppress notifications, and store the response of any external query next to the event so replay sees the value as of then.
- **LiveStore** (client-side event sourcing on SQLite) is the closest to cmd: "the eventlog is the append-only, ordered log of committed events for one store, the source of truth all state derives from"; materialisers "run identically on every client". A change of the schema hash **re-materialises the state tables from the eventlog**, no hand-written migrations. Events are versioned by name (`v1.TodoCreated`) and never edited; synced and client-only events are distinguished; a random `clientId`.
- Dudycz and the Utrecht study list the tactics in use: versioned event types, weak schema (additive fields), upcasting (between deserialise and handle), in-place transform, copy-and-transform. Advice: keep streams short so old schemas age out; deploy in phases (read both, write new, remove old). Reported pains: projection rebuild cost, deletion (GDPR) in an immutable log, the learning curve.
- **Linear**: a global monotonic `lastSyncId` per transaction; sync actions `{id, modelName, modelId, action: I|U|A|D|C|G|S|V, data}`; a `__schemaHash` over model metadata bumps the IndexedDB version and recreates stores; unsent transactions persisted in `_transaction` and replayed on restart; partial indexes make "comments for issue X" possible without ids.
- **cr-sqlite** tracks cells: `crsql_changes(table, pk, cid, val, col_version, db_version, site_id, cl, seq)`; `db_version` is a per-commit Lamport clock. It stores current state plus merge metadata, deliberately not history.
- **Kafka compaction**: ordering never changes, offsets are permanent identifiers, at least the last value per key is kept, tombstones live for `delete.retention.ms`.
- **Figma LiveGraph** subscribes to the Postgres WAL, decomposes each view into single-table subqueries and re-evaluates only those a change touches; identical subqueries are shared. **Notion**: everything is a `block {id, type, properties, content[], parent}`.

**For cmd:** one `events` table as the source of truth with a per-event monotonic sequence as identity, order and subscription cursor; derived tables (turns, sessions, days, FTS) as materialisers keyed by a version, rebuilt by replay. Version events by type and version, upcast on read, never mutate. Design deletion up front (tombstones plus compaction): "delete this secret from an immutable log" is the recurring failure. For live queries, invalidate by table and key touched, not by re-running everything.

## 2. Developer activity and time tracking

Sources: ActivityWatch data model and `aw-server-rust` datastore (docs.activitywatch.net/en/latest/buckets-and-events.html, github.com/ActivityWatch/aw-server-rust/blob/master/aw-datastore/src/datastore.rs); WakaTime FAQ (wakatime.com/faq); Atuin history schema, record store and config (github.com/atuinsh/atuin/blob/main/crates/atuin-client/migrations/20210422143411_create_history.sql, …/record-migrations/20230531212437_create-records.sql, docs.atuin.sh/latest/configuration/config/); Screenpipe architecture (2026, docs.screenpipe.com/architecture); Microsoft Recall security architecture (2024, blogs.windows.com/windowsexperience/2024/09/27/update-on-recall-security-and-privacy-architecture/); Rewind.ai launch coverage (2022, 9to5mac.com/2022/11/02/rewind-ai-records-everything-you-do-mac/); Warp Blocks (docs.warp.dev/terminal/blocks); Wave Terminal `waveobj` (pkg.go.dev/github.com/wavetermdev/waveterm/pkg/waveobj); zsh extended history (endler.dev/2021/history/).

- **ActivityWatch**: `buckets(id, name UNIQUE, type, client, hostname, created, data)` and `events(id, bucketrow, starttime, endtime, data JSON)`; times are nanoseconds since the epoch, UTC; the index became a composite `(bucketrow, starttime DESC, endtime)`. One bucket per watcher per host. **Heartbeats**: a watcher posts the same `data` repeatedly; the server merges into the previous event if the data is identical and within `pulsetime`, extending its duration. Idle is a bucket of its own (`aw-watcher-afk`), joined at query time.
- **WakaTime**: heartbeats on file switch, save and every two minutes of typing; **durations are a read-time derivation** joining heartbeats within a timeout (default 15 min). Only paths and metadata leave the machine.
- **Atuin**: `history(id TEXT PK, timestamp, duration, exit, command, cwd, session, hostname)`, `UNIQUE(timestamp, cwd, command)`; a `session` id per shell; filter modes `global|host|session|directory|workspace`. Sync is a separate generic **record store**: `records(id, parent UNIQUE, host, timestamp, tag, version, data BLOB, cek BLOB)`, a per-host hash chain of encrypted, versioned, tagged blobs, decoupled from the history schema. `secrets_filter` is on by default.
- **Screenpipe**: `~/.screenpipe/db.sqlite` with `frames`, `elements` (accessibility tree, FTS5), `audio_chunks`, `audio_transcriptions`, `speakers`, `ui_events`, `tags`; media as files next to the database. Capture is event-driven (app switch, focus, click, typing pause, clipboard, a 5 s idle fallback) with frame dedup; retention modes `media / lean / all`; "delete range and compact"; a local HTTP API including `/raw_sql`.
- **Recall**: snapshots encrypted individually, keys in an enclave gated by Windows Hello; filters on by default for passwords and cards; delete by time range, app or site; user-set disk cap and retention. Rewind: local only, exclude apps and private browsing.
- **Warp**: a Block is command, output, exit code, cwd, timestamp and duration as one unit. **Wave**: every UI object is a `WaveObj` with `OType`, `OID`, `Version` (optimistic concurrency) and `Meta map[string]any`, persisted in SQLite and broadcast as `WaveObjUpdate{UpdateType, OType, OID, Obj}`. zsh: `: <epoch>:<elapsed>;<command>`.

**For cmd:** sources (pane, browser, files, agent hook, git) and events with start/end in integer UTC plus a payload typed by source. Idle as its own source, "active time" computed at read time. Heartbeat merging for repeated identical observations (foreground process, focused file, URL). Atuin's record store as the template for an envelope independent of the per-type schema. Wave's `Meta` plus `Version` on every object as a cheap stable identity for windows and panes.

## 3. LLM and agent observability

Sources: OpenTelemetry GenAI spans (2025–26, github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md); Langfuse data model (langfuse.com/docs/observability/data-model.md); LangSmith run format (docs.langchain.com/langsmith/run-data-format); Braintrust traces (braintrust.dev/docs/guides/traces); OpenInference span kinds (arize.com/docs/phoenix/tracing/concepts-tracing/otel-openinference/span-kinds); Stripe canonical log lines (2019, stripe.com/blog/canonical-log-lines); wide events / observability 2.0 (2026, greptime.com/tech-content/2026-06-10-wide-events-observability-2-0).

- **OTel GenAI**: span name `{gen_ai.operation.name} {gen_ai.request.model}`; `gen_ai.operation.name` (chat, embeddings, invoke_agent, execute_tool…), `gen_ai.provider.name`, `gen_ai.usage.input_tokens/output_tokens` (with cache and reasoning breakdowns), `gen_ai.response.id`, `gen_ai.conversation.id`; **content** (`gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`) **is opt-in**; tool spans carry `gen_ai.tool.name`, `gen_ai.tool.call.id`, `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`. Still "Development" stability.
- **Langfuse**: observation (span/generation/event, nested by `parent_observation_id`) → trace (`trace_id`) → session (`session_id`); physically "one observations table where each row holds the observation-level data plus a copy of the trace-level attributes", denormalised for filtering; scores attach to one of trace, session, dataset run.
- **LangSmith**: `Run{id, name, run_type, start_time, end_time, first_token_time, inputs, outputs, error, status, trace_id, parent_run_id, parent_run_ids[], child_run_ids[], tags, extra, prompt_tokens, completion_tokens, total_cost…}`; `dotted_order` = `<start>Z<uuid>.<child start>Z<child uuid>…`, one string that sorts a whole trace depth-first and chronologically.
- **Braintrust**: `id`, `root_span_id`, span type in {eval, task, llm, function, tool, score, classifier}; `input/output/expected/metadata/metrics/scores`. **OpenInference**: a required `openinference.span.kind ∈ {LLM, CHAIN, TOOL, AGENT, RETRIEVER, EMBEDDING…}` that tells the UI how to render.
- **Stripe, Honeycomb**: one wide event per unit of work with every high-cardinality field; metrics derived at read time ("you can only group by a dimension you still have"); a hot copy for incident search and a cold columnar copy for months of analytics.

**For cmd:** a turn is a natural wide event: one row per prompt → stop with model, tokens (cache included), cost, tool calls, files, duration, outcome, project, branch, pane, queryable without joins (Langfuse's denormalised copy). Fine-grained hook events as children by parent id with a `dotted_order`-style sort key so a session renders in one indexed scan. Adopt OTel attribute names where they exist (`gen_ai.*`) so exports line up; treat prompt and tool content as separable and blob-offloaded, with ids (`tool_use_id`, `response.id`, `conversation.id`) always in the row.

## 4. The coding agents' own data

Sources: Claude Code JSONL format (2026, adityabawankule.io/blog/claude-code-session-jsonl-format), `~/.claude` layout (2025, gist.github.com/samkeen/dc6a9771a78d1ecee7eb9ec1307f1b52), session continuation (2026, blog.fsck.com/agent-blog/2026/02/22/claude-code-session-continuation/), compaction bug (github.com/anthropics/claude-code/issues/92089); Codex rollouts (2026, codex.danielvaughan.com/2026/06/08/codex-cli-session-lifecycle…, dev.to/milkoor/reverse-engineering-codex-cli-rollout-traces-3b9b); Gemini CLI sessions (geminicli.com/docs/cli/session-management/); Cursor `state.vscdb` growth (2026, forum.cursor.com threads 166013, 167641); Continue dev data (docs.continue.dev/customize/deep-dives/development-data); Amp threads (ampcode.com/docs/threads); VS Code telemetry (code.visualstudio.com/docs/configure/telemetry).

- **Claude Code**: `~/.claude/projects/<cwd with / → ->/<sessionId>.jsonl`, append-only. Every line: `type, uuid, parentUuid, timestamp, sessionId, cwd, gitBranch, version, isSidechain, message`; types `user|assistant|system|summary|file-history-snapshot|attachment|permission-mode|custom-title|agent-name|queue-operation`. Tools link by `tool_use.id ↔ tool_result.tool_use_id`; `toolUseResult.agentId` points at `<session>/subagents/agent-<id>.jsonl`, each its own `parentUuid` chain. Streamed assistant blocks repeat `usage`: dedupe by `message.id`. Compaction writes `system/compact_boundary {logicalParentUuid, compactMetadata{trigger, preTokens}}` then a `user` row with `isCompactSummary: true, isVisibleInTranscriptOnly: true`; a continuation file can carry the parent's `sessionId` in its first rows. `history.jsonl` holds `{display, pastedContents, timestamp, project}`; `~/.claude.json` keeps per-project `lastSessionId, lastCost, lastAPIDuration`.
- **Codex**: `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<id>.jsonl`, each line `{timestamp, type, payload}` with `type ∈ session_meta | response_item | event_msg | turn_context | compacted`; tool calls are flat `function_call`/`function_call_output` paired by `call_id`, **no parent field**; exec output truncated at 10,000 bytes; cold files compressed to `.jsonl.zst`; **a companion SQLite index** (git SHA, `archived_at`, model) reconciled from the files at startup (`reconcile_rollout`); a fork is a new thread id with `forked_from_id` and copied history.
- **Gemini CLI**: `~/.gemini/tmp/<project_hash>/chats/*.jsonl`; `sessionRetention {maxAge: "30d", maxCount: 50}` defaults; shadow-git checkpoints.
- **Cursor**: a key-value store in SQLite (`cursorDiskKV` keyed `composerData:<id>`, `bubbleId:<composer>:<bubble>`, `agentKv:blob:<hash>`, `checkpointId:`); users report 30 GB and 97 GB files (`agentKv` alone 91 GB, 767k rows). Staff: "Cursor doesn't automatically clean up or compact the chat and agent history it saves locally"; deleting chats in the UI freed nothing; VACUUM needed twice the free disk and failed.
- **Continue**: `~/.continue/dev_data/{schemaVersion}/{eventName}.jsonl`, base fields `eventName, schema, timestamp, userId, userAgent, selectedProfileId`; schemas versioned in the repo; a `level: all | noCode` switch strips code. **Amp**: thread ids `T-…` the same across CLI, web and mobile; a handoff makes a new thread with distilled context; commits get an `Amp-Thread-ID` trailer. **VS Code**: every event carries a classification (`SystemMetaData | CallstackOrException | PublicNonPersonalData | EndUserPseudonymizedInformation`) and a purpose; `code --telemetry` dumps the full catalogue.

**For cmd:** the agents already give stable ids (`sessionId`, `uuid`, `parentUuid`, `tool_use_id`; `session_meta.id`, `call_id`): store them verbatim as foreign identities and never re-mint them. Like Codex, treat the JSONL as the agent's property and keep a reconcilable copy and index, so a lost database isn't a lost history. Handle compaction explicitly (boundary and summary rows are not dialogue; dedupe by `uuid`). Cursor is the cautionary tale: blob-heavy state without retention or GC turns "the application file" into a 97 GB liability. Amp's trailer (link commits to the turn that made them) fits cmd's reflog events.

## 5. Memory and knowledge layers over activity

Sources: Graphiti (2024–26, github.com/getzep/graphiti; getzep.com/blog/beyond-static-knowledge-graphs/); Mem0 (2025, arxiv.org/html/2504.19413); A-MEM (2025, arxiv.org/html/2502.12110); Letta/MemGPT (docs.letta.com/guides/agents/architectures/memgpt); *Memory for Autonomous LLM Agents*, a survey (2026, arxiv.org/html/2603.07670); GraphRAG default dataflow (microsoft.github.io/graphrag/index/default_dataflow/).

- **Graphiti**: `EpisodicNode` (the raw text, the ground truth) —`MENTIONS`→ `EntityNode`; an `EntityEdge` carries a natural-language `fact` plus **bi-temporal** fields: `created_at`/`expired_at` (database time) and `valid_at`/`invalid_at` (world time, extracted); a contradiction *expires* the old edge and rewrites its fact rather than deleting; communities cluster entities; retrieval is embeddings + BM25 + graph distance, reranked; incremental, no batch recompute.
- **Mem0**: extraction from (latest exchange, rolling summary, last 10 messages) → candidate facts; an update phase retrieves the 10 most similar memories and has the model choose `ADD | UPDATE | DELETE | NOOP`; the graph variant marks obsolete relations invalid. About 7k tokens per conversation against 26k for full context.
- **A-MEM**: a note is `{content, timestamp, keywords, tags, contextual_description, embedding, links}`; on insert, neighbours are retrieved, a model decides links and *evolves* neighbours' descriptions; retrieval pulls top-k plus linked notes.
- **Letta**: core memory is small editable *blocks* `{label, description, value, limit}` always in context; recall is the searchable full history; archival is a vector store; on overflow, summarise and evict into recall.
- **The survey**: memory as a write–manage–read loop; axes of temporal scope (working, episodic, semantic, procedural), substrate and control. Known failures: **summarisation drift** (details vanish with repeated compression); "long context is not memory" (systems near-perfect on LoCoMo fall to 40–60% on MemoryArena).
- **GraphRAG**: `text_units` (chunks with provenance) → `entities`, `relationships`, optional time-bound `claims`; hierarchical communities with model-written reports at several levels.

**For cmd:** the episodes exist (turns, commands, visits, entries); the missing layer is *facts* with provenance and validity: rows `{fact, entity_refs, source_event_ids[], valid_at, invalid_at, created_at, expired_at, confidence}`, expired rather than deleted, so "why does it think X" is always answerable. Keep Letta-style blocks per project (small, editable, always included) apart from retrieved memory. Build context with a budget: blocks → recent events → retrieved facts (FTS + vectors, fused) → linked neighbours, and emit the chosen sources with the prompt so summaries cite event ids. Regenerate digests from events, never from previous digests alone.

## 6. Search and analytics on SQLite

Sources: FTS5 (sqlite.org/fts5.html); sqlite-vec (github.com/asg017/sqlite-vec); JSONB (sqlite.org/jsonb.html; antonz.org/sqlite-3-45/); *SQLite as an application file format* (sqlite.org/appfileformat.html); detecting changes with `PRAGMA data_version` (sqlite.org/forum/forumpost/62ad06c37b91e068); PowerSync watch queries (docs.powersync.com/client-sdks/watch-queries.md); DuckDB's SQLite extension (duckdb.org/docs/lts/guides/database_integration/sqlite); ATTACH (sqlite.org/lang_attach.html).

- **FTS5**: *external content* tables (`content='events'`) index without duplicating text but need triggers that pass the *old* values on delete and update, or the index silently desyncs; *contentless* (`content=''`) is smallest and supports `contentless_delete=1` now. `detail=full|column|none` took the docs' example from 743 to 340 to 134 MiB; `automerge`, `crisismerge` and the `merge`/`optimize` commands let a long-running writer amortise merging; `trigram` gives indexed substring search.
- **sqlite-vec**: `vec0` virtual tables with float, int8 or bit vectors, metadata columns usable in the KNN `WHERE`, partition keys; brute force only (fine to 10⁵–10⁶ rows); pre-1.0.
- **JSONB** (3.45): 5–10% smaller and under half the CPU of text JSON; an internal format, always read through `json_*`. Generated columns over `json_extract` plus indexes give B-tree speed on payload fields.
- **appfileformat**: single file, atomic writes, incremental updates, concurrent readers; "a clear SQL schema is better documentation than hundreds of pages of custom format spec".
- **Change detection**: `sqlite3_update_hook` sees only the same connection's writes; across connections the recommended method is polling `PRAGMA data_version`. **PowerSync** re-runs watched queries on dependent-table change in three modes: naive, incremental (compare result sets, emit only on change), differential (added/removed/updated).
- **DuckDB** can `ATTACH` a SQLite file and `COPY … TO parquet`; the recurring pattern is cold Parquet for analytics beside the live SQLite. `ATTACH` across files is atomic only outside WAL. SQLite's position: multi-GB files are fine; performance problems are design, not size.

**For cmd:** the core is the single writer, so it can route every write through one connection, hook commits there and publish `(table, seq)` change signals to subscribers, re-running subscribed queries PowerSync-style with a diff. An external-content FTS5 table over the canonical text with correct delete triggers, `detail=column` unless phrase search is wanted, a nightly `merge`. JSONB payloads plus generated columns for the hot fields. Large tool outputs in a content-addressed blob table with the hash on the event row, which is also what makes retention tractable. Hot facts and rebuildable data in separate files, attached for reads.

## 7. Privacy and redaction

Sources: Atuin config (docs.atuin.sh/latest/configuration/config/); Screenpipe privacy data flow and filter (2026, docs.screenpipe.com/privacy-data-flow, docs.screenpi.pe/privacy-filter); Recall (above); ActivityWatch exclude list (forum.activitywatch.net/t/add-an-exclude-list/345); Continue `noCode`; VS Code classification; OTel GenAI content opt-in.

- **Atuin**: `secrets_filter = true` by default with built-in regexes (AWS, GitHub, GitLab, Slack, Stripe, npm, Netlify, Pulumi); user `history_filter` and `cwd_filter` regex lists; `prune` applies new filters retroactively; sync is end-to-end encrypted.
- **Screenpipe**: `deny_apps` and `deny_windows` globs, hot-reloaded; a PII filter replaces with `[PERSON] [EMAIL] [PHONE] [SECRET]` and is applied to every AI-facing search; an explicit list of which features send data off-device; "delete range and compact". Its docs say not to rely on the filter alone: don't record password managers.
- **Recall**: opt-in, per-snapshot encryption with keys gated by biometrics, default filtering, private browsing never captured, delete by range, app or site. **ActivityWatch**: `exclude_title` and regex ignore rules at capture; the philosophy is *don't store it* rather than redact later. **Continue**: `noCode`. **VS Code**: every event classified, a CLI dumps the catalogue. **OTel**: content opt-in; "implementations should provide configuration mechanisms for filtering or truncating content".

**For cmd:** three layers, each visible to the user: (1) capture-time deny rules (apps, titles and URLs by glob, folders, command regexes, the default secret patterns on shell commands and tool inputs and outputs), the only truly safe layer; (2) storage-time redaction with the original dropped, not kept encrypted; (3) read-time filters on what goes to a model. Plus a prune that re-applies new rules to history, delete by range, project or session, and a `cmd data explain` that lists every event type with its classification and whether it ever leaves the machine.

## Patterns that recur

1. An append-only log as the source of truth; everything shown is a derived projection (Kleppmann, LiveStore, Codex's index rebuilt from rollouts).
2. One monotonic sequence number is identity, order and subscription cursor at once (Kafka offsets, Linear `lastSyncId`, cr-sqlite `db_version`).
3. A schema hash triggers re-materialisation of derived tables; events are versioned by name and upcast on read, never rewritten (LiveStore, Linear, Dudycz).
4. Envelope apart from payload: `{id, parent, source/host, type@version, ts, data}` (Atuin records, Codex lines, Claude Code line headers).
5. Interval events with start and end (or ts plus duration) in integer UTC; heartbeat merging for repeated identical observations (ActivityWatch, WakaTime).
6. Idle and "active time" computed at read time from a timeout, never baked in.
7. One wide, denormalised row per unit of work for analytics, child rows for detail (Stripe, Honeycomb, Langfuse).
8. Tree position encoded for one-scan rendering: `parentUuid` chains, `dotted_order`, `parent_run_ids[]`.
9. External ids kept verbatim (`tool_use_id`, `call_id`, `sessionId`, `T-…`); cross-system links by trailers and metadata (Amp, Claude `agentId`).
10. Content opt-in and separable from metadata; large payloads truncated or offloaded to blobs (OTel GenAI, Codex's 10 KB cap, Screenpipe's media files).
11. Compaction and summaries recorded as events pointing at what they replace (Claude `compact_boundary`, Codex `compacted`, Letta recall), never silent rewrites.
12. Facts with bi-temporal validity and provenance; contradictions expire rather than delete (Graphiti, Mem0).
13. Small always-in-context memory blocks apart from retrieved memory (Letta); retrieval hybrid (BM25 + vectors + links) and budgeted.
14. Capture-time exclusion beats later redaction; default secret regexes; retroactive prune; explicit "what leaves the machine" lists (Atuin, Screenpipe, ActivityWatch, Recall).
15. Retention is a first-class setting (Gemini `maxAge/maxCount`, Recall's cap, Screenpipe's modes, Codex's zstd cold files), and the index is reconcilable from the files.

## Anti-patterns, with evidence

- **Unbounded blob-heavy local state with no GC**: Cursor's `state.vscdb` at 30 and 97 GB; deleting chats freed nothing; VACUUM failed; no automatic cleanup (forum.cursor.com 166013, 167641).
- **Compaction that re-appends history**: Claude Code #92089, a second `/compact` re-appended summarised rows, 60% of a 166 MB transcript was duplicates and a day of turns was lost. Boundaries must point, not copy; readers dedupe by id.
- **State stored beside events so it can't be rebuilt**, and the event store used as a message bus mixing technical and business events (an InfoQ post-mortem, 2019); recovery was possible only because storage sat behind a port.
- **Events too fine, replay too costly**; projections not updated for new fields, so replay applied today's rules to old data (the Utrecht study's "projection rebuild" challenge). Snapshots and summary events are the mitigation.
- **Deletion in an immutable log** is a top-four practitioner challenge (arXiv 2104.01146): tombstones and compaction from day one.
- **Causality-free flat logs**: Codex rollouts have no parent id, so pairing relies on `call_id` and time order; Claude's `sourceToolAssistantUUID` resolves only within the subagent file. Store explicit parents.
- **Double counting from streamed records**: Claude's assistant lines repeat `usage` per content block; sum by `message.id`.
- **Summarisation drift**, and "long context is not memory": regenerate digests from primary events.
- **Reactivity through the wrong hook**: `sqlite3_update_hook` misses other connections' writes; a single-writer core avoids this.
- **Redaction as the only defence**: Screenpipe's docs say its filter isn't enough and to exclude password managers at capture; Recall shipped, was pulled, and returned as opt-in with an enclave and filtering.
- **FTS external-content desync**: delete and update triggers must supply the old values or the index diverges silently; contentless tables without `contentless_delete` can't delete.
