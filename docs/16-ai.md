# AI providers and onboarding

> Status (2026-10-05), branch `ai`: plan, nothing built yet. Replaces the Magic-only provider setup described in [14-magic-v2.md](14-magic-v2.md) with one that every part of cmd can use.

Today only Magic widgets talk to a model: the user enters an Anthropic or OpenAI key on the Magic Widgets settings page. More AI features are coming (summaries of what agents are doing, richer "done" notifications, enriched UI in many places), so access to a provider becomes something the whole app depends on, not a Magic setting. This doc plans:

1. a central AI service in the core that every feature calls;
2. models that pick themselves, so a model release doesn't need a cmd release;
3. a first-launch onboarding wizard whose first real step sets up providers, and which later steps (picking a theme, …) extend.

## Design

### Providers and tiers (`packages/protocol/src/ai.ts`)

`AI_PROVIDERS` replaces `MAGIC_PROVIDERS`. Each entry has a title, its key secret, where to get a key, and per-tier model rules (see "Picking models").

Features don't name a model; they ask for a **tier**:

- `smart`: agent loops, Magic. Quality over speed.
- `fast`: summaries, notifications, classification. Cheap and quick.

Two tiers instead of a model setting per feature keeps the settings small however many features arrive. A per-feature override can come later if a feature needs one.

Settings:

| Key | Default | |
|---|---|---|
| `ai.provider` | `anthropic` | the provider features use; the other one only if this one has no key |
| `ai.<provider>.model` | `auto` | the `smart` tier |
| `ai.<provider>.fastModel` | `auto` | the `fast` tier |

Renames (`RENAMED_SETTINGS`): `magic.provider` → `ai.provider`, `magic.<p>.model` → `ai.<p>.model`. Secrets become `ai.<provider>.apiKey`; a `RENAMED_SECRETS` map lets `readSecrets` migrate the file on load and `cmd settings secret` accept the old names.

### Picking models

Both providers list the models a key can use at `GET /v1/models`, with release dates, and we already fetch that list. So a tier names a model **family** and the core uses the newest model of it the key has:

```ts
anthropic: {
  tiers: { smart: [/^claude-opus-\d/], fast: [/^claude-haiku-\d/] },
  fallback: { smart: "claude-opus-5-5", fast: "claude-haiku-4-5" },
},
openai: {
  tiers: { smart: [/^gpt-\d+(\.\d+)?$/], fast: [/^gpt-\d+(\.\d+)?-mini$/] },
  fallback: { smart: "gpt-5.5", fast: "gpt-5.5-mini" },
}
```

`resolveModel(provider, tier)`, in order:

1. **Pinned**: the setting holds a model id, not `auto`. Always wins.
2. **Remote recommendation** (later, optional; below), restricted to models the key has.
3. **Local family patterns**: the first match in the key's list, newest first. Undated aliases only (`isOpenAIChatModel` already drops dated snapshots; do the same for Anthropic), so `claude-haiku-4-5-20251001` resolves to `claude-haiku-4-5`.
4. **Fallback**: the hard-coded id. A failed listing never fails a call.

The resolved list is cached on disk (`ai-models.json` in the state dir), so startup and offline work don't wait on the network. It is fetched again about daily and right after a key changes.

Auto must be visible, or cost and behaviour change silently: the model popup's first entry reads "Auto (Claude Opus 5.6)", and every call logs the model it used.

**Limit:** version bumps (Opus 5.5 → 5.6, GPT-5.5 → 6) need no change; a new family name does. Anthropic's lineup already has Fable next to Opus and Sonnet, which the `opus` pattern never picks. Locally that's a one-line registry change, not a new default id.

**Remote recommendations** (a later step) close that gap: a small JSON file on endtime-instruments.org, where usage stats already go:

```json
{ "anthropic": { "smart": ["claude-fable-*", "claude-opus-*"], "fast": ["claude-haiku-*"] } }
```

A new family, or a release that is bad for our prompts, is then one edit to that file, with no app release. Unreachable, the local patterns still apply.

### The core service (`packages/core/src/ai/`)

`backends.ts` and `models.ts` move here from `magic/`. One service, one instance on `Core`:

```ts
class AiService {
  status(): AiStatus                                   // per provider: key set, verified, resolved models; ready
  complete({ tier, system, prompt, purpose, signal }): Promise<{ text; usage; model }>
  object<T>({ tier, schema, system, prompt, purpose, signal }): Promise<T>   // generateObject
  agent({ tier, system, messages, tools, exec, maxSteps, onText, onTurn, purpose, signal })  // today's Backend.run loop
  models(provider, refresh?): Promise<AiModel[]>
  verify(provider, key): Promise<AiModel[]>            // test a key before storing it
}
```

- **`purpose`** on every call (`"magic"`, `"notify.agentDone"`, `"agents.digest"`): logs, usage and cost totals per purpose, and per-feature on/off.
- **One limiter** for all calls. Interactive calls (Magic, a user waiting) go before background ones (digests), so background features can't flood the provider or slow a Magic run.
- **One error**, `AiNotConfigured`, instead of messages pointing at Magic settings. The UI turns it into "Set up AI…".
- `MagicService` gets `ai: AiService` instead of the `secret` callback; `backendFor` becomes internal.
- The `cmd magic` prompt lab builds an `AiService` from the files, without a core, as it does now.

Protocol (`rpc.ts`):

- `ai.status` → `AiStatus`
- `ai.verify({ provider, key })` → models the key can use, or the provider's error
- `ai.models({ provider, refresh? })`, replacing `magic.models`
- event `ai.updated` (keys, verification or resolved models changed)

### Onboarding

A wizard of steps, shown at first launch, that later releases extend.

- **Registry** (`renderer/src/onboarding/steps.ts`): `{ id, title, Component, existingUsers?: boolean }[]`. First steps: Welcome, AI providers, Done. Theme comes later as one more entry.
- **Where:** a sheet in the first app window, claimed once per launch like What's New (`main/onboarding.ts`). A sheet keeps the app visible behind it; a theme step can preview live. On a fresh install it runs instead of What's New.
- **State:** completed step ids in `onboarding.json` in the UI state dir (as `whats-new.json`). When a release adds a step with `existingUsers: true`, existing users see only that step. Every step can be skipped.
- **AI step:**
  - pick one or both providers, with a link to where to get a key;
  - paste a key: `ai.verify` checks it at once and shows the models it can use;
  - tiers default to Auto, showing what they resolve to;
  - one sentence on what is sent to the provider and when;
  - opt-ins for the background features (below);
  - a key migrated from Magic shows the step as already done.
- **Again later:** a "Set Up cmd…" command in `shared/commands.ts` (menu item and palette), and a button on the Settings AI page.

### Settings window

- New **AI** page: every provider's key row, always shown (no `when:`, several can be configured), the default provider, both tiers per provider (`control: "model"` gains a `tier`), later one switch per background feature.
- The Magic page loses its provider and model rows and points to the AI page.

## First features on top

Separate branches once the service is in.

- **Richer "done" notifications.** When an agent finishes, AI is ready and the feature is on, `ai.object({ tier: "fast", purpose: "notify.agentDone" })` turns the transcript's tail into a title and a line or two. macOS notifications can't be edited after they're posted, so wait briefly (about 2–3 s) and fall back to today's text.
- **Agent digests.** A core service on `AgentTracker` and the transcript sources: every few minutes it summarises agents that changed, kept with the agent for the sidebar and tooltips.

Both send transcript content to the provider: each is off until the user opts in.

## Order of work

1. Protocol `ai.ts`, setting and secret renames with their migrations.
2. Core `ai/`: `complete`, `object`, `agent`, `verify`, `status`, `resolveModel` with its disk cache. Magic and the CLI move onto it. Tests: adapt `providers.test.ts`; migrations, `ai.status`, model resolution (newest of family, aliases over snapshots, pinned, fallback).
3. Settings AI page.
4. Onboarding: registry, sheet, Welcome / AI / Done, the menu command.
5. Later: remote recommendations; notification enrichment; agent digests.

## Open questions

- **Per-feature model overrides:** recommended only when a feature needs one; tiers until then.
- **One default provider:** everything uses `ai.provider`, the other only as a fallback without a key. Per-feature providers if a real need appears.
- **Local and OpenAI-compatible providers** (Ollama, LM Studio, OpenRouter). `magic.baseUrl` was removed on purpose, but background summaries are where a local model helps most (cost, privacy). One more `AI_PROVIDERS` entry with a base URL; in this work or after?
- **Onboarding as a sheet or its own window:** recommended sheet.
